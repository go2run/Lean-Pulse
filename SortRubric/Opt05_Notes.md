# 第 05 次優化 — Notes

## 1. 這一步做了什麼

把成本後條件從**絕對**改成**相對**：

```
✗  require ticksOld = 0  ／  ensures ticks ≤ f arrOld.size
✓  （無 require）        ／  ensures ticks ≤ ticksOld + f arrOld.size
```

對照 F\* 的形狀：`ticks <= i + f (Seq.length s)`。

## 2. ★ 這一步**不防作弊**

十步裡唯一一步。它防的是**不可用**（界限疊不起來），不是**不誠實**。

**第 04 次能通過的作弊，第 05 次一個都沒淘汰**——
歸零、不計費、分身，全部原封不動活著。這一點必須明寫，否則讀者會誤以為它是一刀。

## 3. 副作用：計數器的傳遞方式在這一步定案

`ticksOld` 只有在計數器是 `mut` 參數時才存在。
⇒ **計數器用 `mut` 參數傳，不是 tuple 回傳。**

（實作上兩者等價——`mut` 本來就是 tuple 語法糖，`Velvet/Syntax.lean:330-337`——
但只有 `mut` 形式能在 `ensures` 裡寫出 `ticksOld`。）

## 4. ★ R12 控制組：這一步最重要的方法論動作

### 4.1 為什麼非做不可

第 05 次要示範的失敗（`Opt05_Cheat_NoCompose`）長得**跟一個真實存在的上游 bug 一模一樣**：

| | 症狀 |
|---|---|
| 我們要示範的 | 絕對界限下，第二次呼叫的前條件證不出來 |
| 上游 bug（`UPSTREAM_REPORT.md` Instance 2） | 呼叫 `mut` 參數的 method 時，呼叫端目標被注入 `sorry` |

**兩者都表現為「呼叫端證不出來」。** 沒有控制組，這一步的說服力歸零——
讀者無從判斷失敗是規格造成的還是工具壞掉造成的。

### 4.2 控制組的設計

`Opt05_TicksRelative.lean` §3 的 `sortTwiceRel`：

- **一模一樣的呼叫程式碼**（連續兩次呼叫）
- **一模一樣的呼叫語法**（`let ⟨_, a1, t1⟩ ← …`，即上游 bug 旁邊倖存的那個形式）
- 唯一的差別：被呼叫的是**相對界限**版本
- 結果：✅ **通過**，`#print axioms` 乾淨

⇒ 呼叫機制本身是好的。失敗可以歸因於界限的形式。**歸因成立，不是 INCONCLUSIVE。**

### 4.3 失敗目標讀起來就是全部的論證

```
ensures_1 : x.2.2 ≤ arrOld.size * arrOld.size     ← 第一次呼叫給的【全部】資訊
⊢ i_2 = 0                                          ← 第二次呼叫要求的
```

`i_2` 是第一次呼叫之後的計數。絕對界限只給了**上界**，第二次呼叫要求**等於 0**。

第二則訊息的 case 名字直接把成因寫出來：`case «require_1: ticksOld = 0»`。

**`ticks ≤ f n` 這個形狀，把「計數器從 0 開始」偷偷寫進了前條件**，
於是任何已經花過計數的程式都不能再當它的輸入。
相對界限不談起點、只談增量，所以沒有這個問題。

## 5. 橋接：`triple_cons` 第三次只換投影

| 第幾次 | ensures 數 | 投影 |
|---|---|---|
| 02 | 2 | `⟨h.2, h.1⟩` |
| 04 | 3 | `⟨⟨h.2.2, h.2.1⟩, h.1⟩` |
| **05** | **4** | `⟨⟨h.2.2.1, h.2.1⟩, h.1⟩` |

形狀不變、位置不變，只有投影跟著 `ensures` 的數量走。
**這是選 `triple_cons` 而非 `funext`/`propext`/`▸` 的第三筆佐證**
（後者在三項時就已經失效，見 `Opt02_Notes.md` §3.3）。

第 05 次多了一條 `ensures arr.size = arrOld.size`——proof-friendly redundancy，
給呼叫端用（呼叫端要知道第二次呼叫的 `size` 沒變）。
它可由 `SameElements` 推出，但留著讓 solver 好過，正是指引 §6.2 陷阱 2 的做法。

## 6. 鬆度會累積

| | 實際比較次數 | 宣稱界限 | 比值 |
|---|---|---|---|
| 單次（第 04 次） | 28 | 64 | 2.3× |
| 連續兩次（本次） | **56** | **128** | 2.3× |

`(56, 128)` 已用 `#guard_msgs` 釘住。

排兩次是 28 + 28 = 56——第二次雖然輸入已經排好，**內層迴圈仍固定跑滿 `n` 次**
（沒有提早跳出），資料的有序性一點都沒省到。

> 這延續第 04 次 §5 那一課：**上界太鬆，規格照收，毫無反應。**
> 而組合會把鬆度原樣帶過去。

## 7. 遇到的問題

### 7.1 `#guard_msgs` 釘多則訊息用 `---` 分隔

本步的失敗會產生**兩則**訊息（一則 `Failed to prove assertion`、
一則 `unsolved goals`）。`#guard_msgs` 的 docstring 用 `---` 分隔即可一次釘住兩則。
已進 ERRATA。

### 7.2 一個算錯的預測（已更正）

原本預期連續兩次是 28 + 8 = 36，理由是「第二次已排好」。
**錯的**——內層迴圈沒有提早跳出的機制，永遠跑滿 `n` 次，所以是 28 + 28 = 56。
`#guard_msgs` 當場抓到（`- info: (36, 128)` / `+ info: (56, 128)`）。

> 附帶說明了為什麼 witness 要用 `#guard_msgs` 而不是 `#eval` 加註解：
> **釘住的數字會反駁你，註解不會。**
